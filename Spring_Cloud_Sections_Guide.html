Port quick guide

8080 Tournament HTTP port when run locally. In Docker this is usually the container-side port; Compose can publish it under another host port.
8081 Team HTTP port. It differs from Tournament 8080 so both apps can run on your computer at the same time.
8082 / 8084 Second Tournament instance. Local Java run uses 8082; Docker Compose publishes container port 8080 as host port 8084.
8083 Host-side port for the standalone image test. Mapping 8083:8080 avoids a conflict with a local app already using 8080.
8761 Eureka registry address and dashboard. Services register here so other services can discover their names and instances.
8888 Gateway HTTP port. Clients send one request here; Gateway forwards it to Team or Tournament.
9999 Config Server HTTP port. Apps request their profile settings from this port when they start.
3306 MySQL database listener. Use it from Windows only when Docker publishes 3306 to the host; containers connect to MySQL by service name.
5672 RabbitMQ AMQP port used by applications to publish/consume messages; 15672 is the human-facing management page.
8090 Keycloak URL from your browser/Postman. Docker forwards host 8090 to Keycloak container port 8080.
9010 Message has this configured server port, but its final project has no web starter or REST controller. Test it by sending an event through Team and RabbitMQ.

2. Service-to-service communication

Target: When you request a Team, Team also looks up that team's tournament and returns both records. This is synchronous request/response: the Team service waits for Tournament to answer before it can finish its own response.

Main files: Team TeamServiceImpl.java coordinates the two calls; TeamMicroserviceApplication.java creates the WebClient bean and enables Feign; APIClient.java declares the Feign request; Team pom.xml adds WebFlux and OpenFeign.

Approach 1: WebClient

WebClient is Spring's HTTP client. In the WebClient version, Team builds a GET request to http://localhost:8080/api/tournaments/PL, reads the JSON response into TournamentDto, then combines it with the Team data. The project registers WebClient as a Spring bean so the service can inject and reuse it. The code ends with .block(), so this particular call waits for the response even though WebClient can also be used reactively without blocking.

Approach 2: OpenFeign

OpenFeign lets you describe the same HTTP call as a Java interface. APIClient.java gives the base address and maps a Java method to GET /api/tournaments/{tournament-code}. Spring generates the HTTP client implementation. Team calls the method and receives a TournamentDto without writing the request-building steps.

How your SECTION_03 code chooses: Both versions are in TeamServiceImpl.java. It tries the Feign client first; the WebClient branch is used only if the Feign client is unavailable. So with the normal project startup, this workspace uses OpenFeign. The PDF first teaches WebClient, then replaces it with Feign.

Why these ports: Team listens on 8081, so Postman/browser calls /api/teams/1 there. Tournament listens on 8080, so Team sends its internal HTTP request there. They must use different ports because both apps run on the same computer. In this section, localhost works because both apps run directly on Windows; inside Docker, localhost would mean the current container, so later sections use Docker service names or Eureka.

Part 2: Architectural Deep-Dive & Port Rationalization

A rigorous, end-to-end breakdown of the microservices system built across the 13 course sections. This guide analyzes how our distributed system evolved from basic REST endpoints into a resilient, containerized, secured, and event-driven enterprise architecture, explaining the engineering rationale behind every chosen port, protocol, and network topology.

Phase 1 • Sections 01 to 06

Microservices Foundation, Discovery & Containerization

Phase 1 establishes the architectural baseline of our distributed system. We moved away from monolithic design by splitting domain responsibilities into independent services, establishing point-to-point communication, introducing centralized dynamic service discovery, adding edge routing, externalizing configuration, and packaging applications into portable Docker images.

Section 1: Microservices Creation (SECTION_02_CREA_MS) 📄 01+Création+des+microservices.pdf Spring Boot • Spring Data JPA • H2

What we did: We developed two completely decoupled Spring Boot applications: tournament-microservice and team-microservice. Each service owns its own database schema, domain models, and REST controllers:

  • Tournament Microservice: Manages tournament competitions. Entity Tournament stores id, tournamentCode (e.g., PL, CL), tournamentName, and tournamentDescription. Seeded at startup with Premier League and Champions League.
  • Team Microservice: Manages clubs and teams. Entity Team stores id, teamName, tournamentCode, and coach details. Seeded with Arsenal (linked to tournament PL).

Port Selection Rationale (8080 vs 8081): Standard Spring Boot defaults to port 8080. If both applications attempted to run on 8080 simultaneously on a single operating system, the second process would immediately crash with java.net.BindException: Address already in use. We assigned port 8080 to Tournament and explicitly configured server.port: 8081 for Team, allowing both JVMs to run side-by-side on localhost.

Section 2: Synchronous Service-to-Service Communication (SECTION_03_COMM_MS) 📄 02+Communication+entre+les+microservices+avec+Spring+Cloud.pdf WebClient • Spring Cloud OpenFeign

What we did: In a microservices architecture, a single business transaction often requires data owned by multiple services. When a client requests a team via GET /api/teams/1, the Team service must dynamically fetch the associated Tournament data and assemble a unified response (ResponseDto containing both teamDto and tournamentDto).

  • Approach A (WebClient): Reactive HTTP client provided by Spring WebFlux. We injected a WebClient bean and called .get().uri("http://localhost:8080/api/tournaments/" + code).retrieve().bodyToMono(TournamentDto.class).block().
  • Approach B (Declarative OpenFeign): Replaced imperative HTTP code with an interface annotated with @FeignClient(value = "TOURNAMENT-MICROSERVICE", url = "http://localhost:8080"). Spring dynamically generates the proxy implementation at runtime.

Why this matters & its limitation: Hardcoding url = "http://localhost:8080" creates rigid network coupling. If the Tournament service changes host, fails, or scales to multiple instances, the Team service breaks.

Section 3: Dynamic Service Discovery with Eureka (SECTION_04_EUREKA) 📄 03+Spring+Cloud+Netflix+Eureka.pdf Netflix Eureka • Client-Side Load Balancing

What we did: We eliminated hardcoded addresses by introducing Netflix Eureka Server (eurekaserver). Both Tournament and Team became Eureka clients (@EnableDiscoveryClient). They register their service names (TOURNAMENT-MICROSERVICE, TEAM-MICROSERVICE) with Eureka upon startup and send periodic heartbeats every 30 seconds.

Dual-Instance Testing: We launched two concurrent instances of Tournament:

  • Instance 1 running on port 8080.
  • Instance 2 packaged as a JAR and launched with --server.port=8082.

Port Selection Rationale (8761, 8080, 8082, 8081): Port 8761 is the universally recognized convention for Eureka. Port 8082 was selected for Tournament Instance 2 to avoid port collision with Instance 1 (8080) and Team (8081). When Team makes Feign calls, it queries Eureka on 8761 to resolve available instances, and Spring Cloud LoadBalancer automatically balances traffic between 8080 and 8082.

Section 4: Edge Routing with Spring Cloud Gateway (SECTION_05_GATEWAY) 📄 04+Spring+Cloud+Api+Gateway.pdf Spring Cloud Gateway • Reactive Netty

What we did: We built an API Gateway (gatewayserver) built on Netty and Spring WebFlux. Gateway serves as the single unified entry point for all frontend applications and external clients.

Dynamic Route Configuration: Instead of clients calling microservices directly on individual ports (8080, 8081, 8082), clients send all requests to Gateway on port 8888. Gateway inspects the URL path and queries Eureka to route the request:

  • Path /api/tournaments/** → routed to lb://TOURNAMENT-MICROSERVICE
  • Path /api/teams/** → routed to lb://TEAM-MICROSERVICE

Port Selection Rationale (8888): Port 8888 is established as the public perimeter gateway port. Internal service ports (8080, 8081) remain private backend addresses.

Section 5: Centralized Configuration Server (SECTION_06_CONFIGSERVER) 📄 05+Spring+Cloud+Config+Server.pdf Spring Cloud Config • Profile Management

What we did: We separated application source code from environment-specific configuration by introducing configserver. Config Server serves externalized YAML property files (such as tournament-prod.yml and team-prod.yml) over HTTP.

Port Selection Rationale (9999): High port 9999 isolates configuration infrastructure from application runtime ports (8080s) and discovery (8761). On bootstrap, microservices query http://localhost:9999/{application}/{profile} to fetch build versions, author metadata, and database credentials before launching their Spring application context.

Section 6: Container Packaging with Docker (SECTION_07_Intro_to_Docker) 📄 06+Introduction+à+Docker_v2.pdf Docker • OCI Image • OpenJDK Slim

What we did: We packaged tournament-microservice into an immutable Docker image (rayen/tournament:v1) using a multi-stage Dockerfile based on OpenJDK 21. We launched it as a standalone container.

Port Selection Rationale (8083:8080): Mapping host port 8083 to container port 8080 ensures that running the containerized service on the developer's workstation will not collide with any local IDE or Java process already occupying port 8080 on the host.

Section 8: Full Stack Docker Compose Orchestration (SECTION_09_DOCKERIZE_VOS_MS) 📄 08+Dockerize+vos+Micorservices_V2.pdf Docker Compose • Healthchecks • Failover

What we did: Managing multiple standalone docker run commands is fragile. We created a comprehensive docker-compose.yml file orchestrating 6 interrelated services: eurekaserver, configserver, tournaments-ms, tournaments-ms2, teams-ms, and gatewayserver.

Healthchecks & Startup Sequencing: We added Actuator healthchecks (curl -f http://localhost:.../actuator/health) and configured depends_on: { condition: service_healthy } so dependent microservices only launch after Config Server and Eureka are fully operational.

Port Mapping Analysis:

  • tournaments-ms maps container port 8080 to host port 8080.
  • tournaments-ms2 maps container port 8080 to host port 8084.

Why 8084? Inside the Docker network, both containers have distinct IP addresses and can listen on 8080 concurrently without conflict. However, when publishing ports to the single host OS network interface, each host port must be strictly unique. Mapping Instance 2 to 8084 satisfies this requirement.

High Availability Verification: We executed docker compose stop tournaments-ms. Gateway immediately detected the remaining healthy instance and continued routing all requests through tournaments-ms2 with zero downtime.

Section 9: Dynamic Configuration with Spring Cloud Bus & RabbitMQ (SECTION_10_Cloud Bus) 📄 09+Spring+Cloud+Bus+et+Rabbit+MQ.pdf RabbitMQ • Spring Cloud Bus • AMQP

What we did: In a production cluster with dozens of microservice instances, changing a property in Config Server requires either restarting every container or calling /actuator/refresh on every single instance individually. Spring Cloud Bus solves this by connecting all microservices to a lightweight message broker (RabbitMQ).

Port Selection Rationale (5672 & 15672):

  • 5672: Standard binary AMQP port used by Spring Cloud Bus to broadcast and consume messages.
  • 15672: RabbitMQ Web Management Console port for developers to inspect queues and exchanges.

The Refresh Sequence: We updated author.name in team-prod.yml. We then sent a single POST http://localhost:8080/actuator/busrefresh. Tournament published a RefreshRemoteApplicationEvent to RabbitMQ. The Team service consumed the event and dynamically updated its injected @ConfigurationProperties live without requiring a JVM restart.

Section 10: Fault Tolerance with Resilience4J (SECTION_11_Resilience4J) 📄 10+Résilience+des+microservices+avec+Resilience4J.pdf Resilience4J • Circuit Breakers • Fallbacks

What we did: In distributed architectures, downstream service outages cause cascading failures (thread pool exhaustion, timeouts, and system crashes). We implemented Resilience4J Circuit Breaker, TimeLimiter, and Fallback patterns across two protective tiers:

  1. Service-to-Service Tier (Team → Tournament): When all Tournament instances were shut down, Team's Feign client intercepted the failure and executed getTournamentFallback(), returning the team record with tournamentName: NOT AVAILABLE instead of crashing.
  2. Edge Gateway Tier (Gateway → Team): When Team was stopped, 10 consecutive requests exceeded Gateway's 50% failure threshold, causing the circuit breaker to transition from CLOSED to OPEN state. Subsequent calls were fast-failed with HTTP 503 and a clean fallback message: "An error occurred. Please contact the administrator. !".

Phase 3 • Sections 11 to 13

Enterprise Security & Asynchronous Event Architecture

Phase 3 completes the enterprise architecture with two critical capabilities: zero-trust perimeter security using Keycloak Identity & Access Management (OAuth2/OIDC) and asynchronous event-driven choreography using RabbitMQ and Spring Cloud Stream.

Section 11: Securing API Gateway with Keycloak (SECTION_12_Securing_gateway) 📄 11++Securing+microservices.pdf Keycloak • OAuth2 Resource Server • JWT • RBAC

What we did: Microservices should never be exposed unauthenticated to the public internet. We configured Spring Cloud Gateway as an OAuth2 Resource Server backed by Keycloak IAM.

Port Selection Rationale (8090 vs 8080): Inside Docker, Keycloak listens on port 8080. If published directly as 8080:8080 on the host machine, it would clash with tournaments-ms (which also uses 8080). We mapped Keycloak to host port 8090 (8090:8080). Developers access the Keycloak Admin Console at http://localhost:8090/admin/, while Gateway sits on port 8888.

Authentication & Role-Based Access Control (RBAC):

  • Clients authenticate against Keycloak using the OAuth2 client_credentials grant and receive a digitally signed JSON Web Token (JWT).
  • When a request reaches Gateway (8888), Gateway intercepts it via reactive security filters and verifies the cryptographic signature against Keycloak's JSON Web Key Set (JWKS) certificates endpoint.
  • We authored a custom KeycloakRoleConverter that extracts realm roles from the token's realm_access.roles claim array and converts them to Spring Security GrantedAuthority objects.
  • Role Rule for Tournament: Route /api/tournaments/** strictly requires ROLE_ADMIN. Validated: non-admin tokens receive 403 Forbidden; admin tokens receive 200 OK.
  • Authentication Rule for Team: Route /api/teams/** requires valid authentication (any authenticated token).
  • Unauthenticated requests receive 401 Unauthorized.

Section 12: Production Security with PostgreSQL Persistence (SECTION_13_Securing_Docker) 📄 13++Securing+microservices+using+docker.pdf PostgreSQL • Named Docker Volume • Container Isolation

What we did: In Section 11, Keycloak stored its realm data in an ephemeral in-memory database, meaning all clients, secrets, and roles were wiped whenever containers stopped. In Section 12, we hardened the deployment by backing Keycloak with an enterprise PostgreSQL database container (keycloakdb) attached to a named Docker volume (kc_pg_data).

Port Selection & Network Isolation (5432): PostgreSQL listens on standard port 5432. Crucially, port 5432 is not published to the host OS. It is accessible exclusively within the internal Docker network rayen-net, safeguarding the identity database from external network probes.

Persistence Verification: We created the tournament-app client and assigned the ADMIN role. We then executed docker compose down --remove-orphans, destroying all running containers. Upon running docker compose up -d, Keycloak reconnected to the kc_pg_data volume, and our configured client, secret, and roles remained completely intact without requiring any re-creation.

Section 13: Asynchronous Event-Driven Microservices (SECTION_14_Event_RabbitMQ) 📄 14+event+driven+ms+using+RabbitMQ.pdf Spring Cloud Stream • RabbitMQ • Functional Choreography

What we did: Synchronous REST calls (such as Feign) introduce blocking threads and tight temporal coupling: if a downstream notification service is slow or down, the user's creation request hangs. We transformed this into an asynchronous event-driven architecture using Spring Cloud Stream 4.x and RabbitMQ, introducing a dedicated message-microservice.

Port Selection Rationale:

  • 5672: RabbitMQ AMQP broker port carrying business event payloads.
  • 15672: RabbitMQ Management UI to observe message queues in real time.
  • 8888: Secure Gateway entry point.
  • 8090: Keycloak IAM server.
  • 9010 (Internal): Configured application port for message-microservice. Message service operates as a pure event subscriber/publisher; it has no web starter or HTTP controllers.

The End-to-End Asynchronous Choreography:

  1. Client sends authenticated POST http://localhost:8888/api/teams/create with new team details.
  2. Team service persists the record into database with initial status communicationDone = false.
  3. Team service publishes a TeamMsgDto JSON message to RabbitMQ exchange send-communication (via functional binding sendCommunication-out-0).
  4. Client immediately receives 201 Created response (zero blocking, high throughput).
  5. message-microservice consumes the message from queue send-communication.message, executes SMS/Email notification functions (MessageFunctions.java), and publishes a confirmation event to exchange communication-sent (via binding email-out-0).
  6. Team service consumes the callback from queue communication-sent.teams-ms, loads the team by ID, and updates the database row to communicationDone = true.
  7. Client verifies the asynchronous completion by sending GET /api/teams/2, confirming teamDto.communicationDone: true.
